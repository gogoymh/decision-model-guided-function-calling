# 수정 한도 선택 실험

수정 한도 `r`은 최초 제안 이후에 허용하는 수정 횟수입니다. **JBFC**의 개발 정확도로 한도를 고른 뒤, 여섯 테스트 방법의 공통 수정 예산으로 사용합니다. Direct는 수정하지 않습니다.

**JBFC**는 제안을 최대 `r+1`개 만들며 필요한 Jev 검사와 스키마 검사를 모두 통과하면 일찍 종료합니다. 호출이 있으면 함수·인자 검사를 모두 수행하고, no-call이면 인자 검사를 생략해 함수 검사만 적용합니다. 인자 판정·확률은 `null`, `arguments_skipped=true`로 기록하며, 개발 기록을 재검증할 때도 이 구분을 확인합니다. 실패한 이전 후보와 실제 Jev 피드백은 시간순으로 누적해 원래 사용자 요청 앞에 붙입니다. 최초 요청은 변경하지 않고 수정 중에는 함수를 실행하지 않습니다. 구현에는 3회라는 고정 상한이 없습니다.

## 기본 선택 규칙

1. 고정된 BFCL 개발 집합 303개를 같은 설정으로 3회 실행합니다. 이 단계에서는 **JBFC**만 사용합니다.
2. 기본 후보는 `0,1,2,3,4,5`회입니다. 가장 큰 후보 한도로 기록을 만들고 각 한도에서 끝나는 앞부분을 비교합니다.
3. 각 후보의 최종 호출 정확도를 계산합니다. `live_relevance` 1개는 함수·인자 정답이 없으므로 제외합니다. 정확도 분모는 302개 × 3회 = 906개입니다.
4. 개발 정확도가 가장 높은 한도를 고릅니다. 정확히 동점이면 더 작은 한도를 선택합니다. 비용이 알려지지 않아도 이 규칙은 적용할 수 있습니다.
5. 후보별 측정값, 선택한 한도, 설정과 개발 자료의 해시를 선택 파일에 저장합니다.
6. 선택 파일을 검증한 뒤 테스트 집합 2,748개를 3회 실행합니다. 여섯 비교 방법 중 모든 수정 방법에 같은 한도를 적용하며, Direct는 최초 제안만 사용합니다. 전체 테스트는 **2,748개 × 3회 × 6방법 = 49,464개 방법별 기록**입니다.

개발 실행 자체는 **303개 × 3회 = 909개 기록**이며, 위 3번의 선택 점수에만 906개를 사용합니다. **JBFC**의 개발 정확도로 한도를 고정하며 테스트 결과로 다시 선택하지 않습니다. 다른 비교 방법마다 최적 한도를 따로 찾는 실험은 아닙니다.

기본 후보의 최댓값 5도 방법의 고정 상한이 아닙니다. 후보 범위는 개발 실험 전에 바꿀 수 있습니다. 기본 실험은 Noul의 긍정 확률 임계값을 `0.8`로 유지합니다. 다른 임계값·모델·프롬프트를 사용하려면 새 개발 실험으로 한도를 다시 선택합니다.

## 실행

```bash
make check-config
make smoke
make tune
make experiment
```

`make tune`은 **JBFC** 개발 실험과 선택까지만 수행합니다. `make experiment`는 같은 단계를 재개한 뒤 여섯 방법의 테스트를 수행합니다. 키가 필요한 명령이며, `check-config` 자체는 네트워크 요청을 보내지 않습니다. `smoke`는 연결 확인을 위한 부분 실행으로 선택 자료로 사용할 수 없습니다.

기본 파일 위치는 다음과 같습니다.

| 위치 | 내용 |
|---|---|
| `results/tuned/dev_budget/` | 최대 후보 한도의 전체 개발 기록 |
| `results/tuned/repair_budget_selection.json` | 검증 가능한 한도 선택 결과 |
| `results/tuned/test_selected/` | 선택한 한도에서의 전체 테스트 비교 |

후보 범위를 바꾸려면 새 저장 위치를 사용합니다.

```bash
make experiment REPAIR_GRID=0,1,2,4,8 RESULTS_DIR=results/wider_budget
```

기본 논문은 후보 `0,1,2,3,4,5`를 선언합니다. 다른 후보 범위의 실험은 결과 요약까지 생성하며, 논문 표를 자동으로 채우려면 원고의 실험 조건과 보고 검증 규칙도 그 범위에 맞게 바꿔야 합니다.

이미 완료한 개발 기록의 선택만 다시 계산할 수도 있습니다. 이 명령은 모델을 호출하지 않습니다.

```bash
uv run python scripts/tune_repair_budget.py results/tuned/dev_budget \
  --grid 0,1,2,3,4,5 --output results/tuned/repair_budget_selection.json
```

## 기록을 재사용할 수 있는 이유

모델의 프롬프트에는 수정 한도가 들어가지 않습니다. 수정 중에는 함수도 실행하지 않습니다. 매번 누적하는 이전 후보·피드백과 보존한 원본 요청은 같은 기록의 앞부분에서 동일합니다. 따라서 같은 모델·임계값·프롬프트에서 더 작은 한도를 비교할 때는 앞부분의 제안과 피드백이 달라지지 않습니다. 개발 선택에는 **JBFC** 기록만 사용합니다. 일찍 통과한 기록은 모든 더 큰 한도에서도 그 지점에서 종료합니다. 선택 점수와 시간·사용량은 해당 종료 지점까지만 계산합니다.

이 방법으로 아직 기록하지 않은 더 큰 한도나, 바뀐 임계값·프롬프트의 결과를 만들 수는 없습니다. 선택된 한도보다 작은 테스트 한도와 `abstain`의 추가 비교는 효과를 설명하기 위한 분석이며, 이를 이용해 선택값을 다시 고르지 않습니다.

여섯 테스트 방법은 사례·반복별로 같은 최초 LLM 제안 하나를 공유합니다. 비용 비교에는 각 방법이 처음부터 실행되었다면 필요한 호출과 누적 피드백의 입력 토큰을 모두 포함하고, 개발 탐색 비용은 테스트 비용과 나누어 보고합니다. 공유하거나 재사용한 호출을 공짜 호출로 취급하지 않습니다.

## 검증과 결과 해석

선택에는 전체 개발 자료와 완전한 반복 기록이 필요합니다. 테스트 집합, 일부 사례만 실행한 기록, 합성 데모, 중복·누락·설정 불일치가 있는 기록은 선택 자료로 허용하지 않습니다. 선택 파일의 원본 기록과 해시를 검증하고 선택을 다시 계산한 뒤, 모델·API·임계값·코드·데이터·분할·반복 설정이 테스트 실행과 맞는지 검사합니다. 선택 파일은 테스트 실행 지문에도 포함됩니다.

정답은 오프라인 채점과 한도 선택에만 사용합니다. 모델에는 원본 요청, 함수 목록, 제안과 실제 검사 피드백만 전달하며, 정답·선택 파일·개발 성능·테스트 점수는 전달하지 않습니다. 수정 입력은 모든 이전 후보와 피드백을 오래된 순서대로 담은 사용자 메시지 하나를 원본 대화 앞에 추가하고, 원래 메시지 내용·순서를 보존합니다. 모든 후보가 미실행 상태임을 명시합니다. 이 프롬프트 계약이 바뀌면 코드 해시도 바뀌므로 기존 결과에 이어 쓸 수 없습니다.

개발 정확도는 한도를 선택하기 위한 값입니다. 선택 이후의 성능 주장은 별도 테스트 결과를 근거로 해야 합니다. `r=0`이 선택될 수 있으며, 이는 현재 후보와 개발 자료에서 수정이 정확도를 높이지 못했다는 결과일 수 있습니다. 더 넓은 후보 범위나 다른 개발 자료에서는 선택값이 달라질 수 있으므로 이를 보편적인 최적값이라고 주장하지 않습니다.

현재 실제 모델 실험과 한도 선택은 실행하지 않았습니다. 원고에는 후보 목록과 빈 결과표만 있으며, 선택된 한도나 성능 수치는 만들어 넣지 않습니다.
