\begin{abstract}
Function-calling models must choose a function and input values that match the user's request. Correct format alone does not ensure correct choices. We present Jev-Backed Function Calling (\textbf{JBFC}), an inference-time method that uses TypeSafe's System One (Decision) model \textit{Jev} to check an LLM's proposed call. \textit{Jev} checks function choice and, when a call is present, its arguments with binary questions. If a required check fails, we add the proposal and judgments to a growing history placed before the original user request. The LLM uses this feedback to revise both the function and arguments. Acceptance requires all applicable binary checks and the schema check to pass on the same proposal. The repair limit is fixed at three. Our code compares seven methods on a 3,051-example Berkeley Function Calling Leaderboard (BFCL) subset, measuring call correctness, function choice, argument correctness, time, and cost. In one run with \texttt{gpt-5-nano}, \textbf{JBFC} raises call accuracy over direct calling from 63.8\% to 74.6\%, mostly by avoiding unnecessary calls, at about four times the cost. It has the highest call accuracy of the seven methods, and keeping all earlier feedback adds 1.1 points over showing only the latest rejection. With the larger \texttt{gpt-5.4-mini}, it raises mean accuracy over three runs from 81.1\% to 82.1\%.
\end{abstract}

\section{Introduction}
To carry out a user's request correctly, a function-calling system must choose the right function and provide the right argument values. A language model, called the generator, makes these choices. However, a call can have the required format and still use the wrong function or values. For example, a travel assistant may choose the wrong booking function or swap the departure and destination. A JSON schema check verifies required inputs and their types, but cannot guarantee that the call matches the user's request.

Tool-use training and evaluation have improved function-calling systems~\cite{patil2024gorilla,qin2024toolllm,patil2025bfcl}. Even so, the generated function and arguments can still be wrong. We study whether checks from a separate decision model can guide the LLM to improve its next proposal before execution.

\textbf{JBFC} uses \textit{Jev}, TypeSafe's System One model, to answer binary questions about an LLM's function choice and arguments~\cite{typesafe2026models}. When a check fails, we keep the proposed call and its judgments and place all earlier records before the original user request. The LLM then proposes a new call using this accumulated feedback. It can change both the function and argument values. \textbf{JBFC} accepts a proposal only when all applicable binary checks and the schema check pass on that proposal.

Earlier work already uses checks and feedback to fix calls. ToolVerifier checks tool choice and parameters~\cite{mekala2024toolverifier}; ToolCritic gives feedback on tool-use errors~\cite{hamad2025toolcritic}. ReAct uses reasoning, actions, and observations to guide later steps~\cite{yao2023react}. \textbf{JBFC} also carries feedback forward in the prompt, but its feedback comes from checking proposed calls before execution. Our contribution is this specific use of two \textit{Jev} judgments and accumulated prompts, together with an evaluation of its effects and costs.

We compare \textbf{JBFC} with direct calling, schema repair, self-revision, single-check versions, and a latest-feedback version. A fixed repair limit of three controls the comparison. We measure errors fixed or introduced by repair, and keep call correctness separate from acceptance, time, and cost.

\paragraph{Tool use and benchmarks.}
Gorilla studies API-call generation~\cite{patil2024gorilla}; ToolLLM studies tool-use training and evaluation~\cite{qin2024toolllm}. BFCL tests function calling across many settings~\cite{patil2025bfcl}. We use its single-turn Python categories to study decisions made before a function runs. API-Bank offers dialogues with executable API calls~\cite{li2023apibank}. StableToolBench uses caching and simulation to handle changing APIs~\cite{guo2024stabletoolbench}. These suggest broader tests beyond our BFCL subset.

\paragraph{Checks and feedback.}
Self-Refine uses self-generated feedback~\cite{madaan2023selfrefine}, Reflexion uses written feedback~\cite{shinn2023reflexion}, and CRITIC uses feedback from tools~\cite{gou2024critic}. Self-correction can turn correct answers into wrong ones~\cite{huang2024selfcorrect}, so we measure both fixes and new errors. ToolVerifier compares alternatives to check tool choice and parameters separately~\cite{mekala2024toolverifier}. ToolCritic identifies tool-use errors and returns feedback~\cite{hamad2025toolcritic}. \textbf{JBFC} checks complete proposals with a fixed external model through an API and limits repairs.

\paragraph{Accumulated prompts.}
ReAct combines reasoning with actions and observations from an environment~\cite{yao2023react}. Our method uses a similar idea of carrying earlier feedback into the next prompt. Each record contains a proposed function call and verification results, rather than an execution result. The LLM receives all records before the unchanged user request. We do not require a generated reasoning trace or run functions during repair. Many-shot in-context learning often improves as prompts grow to hundreds or thousands of examples, and model-generated rationales kept only when their answers are correct can stand in for human-written ones~\cite{agarwal2024manyshot}. Our records are likewise model-generated examples, labeled by \textit{Jev} instead of reference answers.

\paragraph{\textit{Jev} as a judge.}
Li et al.'s \emph{JEV-as-a-Judge}~\cite{li2026jevjudge} checks finished outputs with probabilities for defined verdicts. If a verdict is uncertain, an independent, stronger judge decides. With fixed rules for when to use the stronger judge, it lowers judging cost while keeping similar accuracy on some tasks. It has limits on difficult reasoning, misleading answer styles, and writing judged without reference information. The study does not test tool or action selection inside agents. \textbf{JBFC} checks proposed function calls and returns failed checks to the same generator for revision. We test the specific design of \textbf{JBFC}.

\section{Method}
\subsection{Propose and Check a Call}
Let $x$ be the user request, $\mathcal{F}$ the available functions, and $G$ the generating LLM. A proposal is $c_t=(f_t,a_t)$, with function $f_t$ and arguments $a_t$, or $c_t=\varnothing$ for no call. We study single-call-or-no-call decisions.\footnote{We treat single-turn decisions as the basic unit of function calling. Parallel calling combines multiple such decisions, while multi-turn interactions repeat them with updated context. We therefore evaluate the verification and repair loop on this basic unit and exclude parallel and multi-turn settings from this study.} Local code checks readability, function availability, required arguments, and types. Write $S(c_t)=1$ when these checks pass.

\paragraph{Binary verification: \textbf{JBFC}.}
For each readable proposal, one \textit{Jev} request checks the function choice and, when a call is present, its arguments:
\begin{align}
 c_t&=G(H_t,x,\mathcal{F}),\\
 p_f^{(t)}&=J_f(x,\mathcal{F},c_t),\qquad
 p_a^{(t)}=J_a(x,\mathcal{F},c_t).
\end{align}
Here $H_t$ contains earlier proposals and feedback and is initially empty. The function \texttt{Noul} question asks whether the function choice, including no call, fits the request. The argument question checks required values, their support in the request, and their parameter roles. For no call, it is skipped and $p_a^{(t)}$ is undefined. A selected function with missing arguments still receives both checks. Both must pass for a call.

\subsection{Accept or Repair a Call}
Acceptance requires the schema check and all required \textit{Jev} checks to pass on the same proposal. The acceptance rule is
\begin{equation}
 A_t=\begin{cases}
 S(c_t)\,\mathbf{1}[p_f^{(t)}\geq\tau_f], & c_t=\varnothing,\\
 S(c_t)\,\mathbf{1}[p_f^{(t)}\geq\tau_f]\,
 \mathbf{1}[p_a^{(t)}\geq\tau_a], & \text{otherwise}.
 \end{cases}
\label{eq:gate}
\end{equation}
\texttt{Noul} returns the probability of yes, with no separate confidence field~\cite{typesafe2026noul,typesafe2026confidence}. We use $\tau_f=\tau_a=0.5$, chosen after runs at 0.8 and 0.7 (Section~\ref{sec:data}).

\begin{algorithm}[t]
\caption{\textbf{JBFC}: verification and prompt repair}
\label{alg:jbfc}
\footnotesize
\begin{algorithmic}[1]
\Require Request $x$, functions $\mathcal{F}$, generator $G$, \textit{Jev} $J$,
\Statex \hspace{\algorithmicindent}repair limit $r$, thresholds $\tau_f,\tau_a$
\State $H\gets[\,]$
\For{$t=0,\ldots,r$}
  \State $c\gets G(\mathrm{Prefix}(H,x),\mathcal{F})$
  \State $(s,e,\mathrm{readable})\gets\mathrm{SchemaCheck}(c,\mathcal{F})$
  \State $p_f,p_a\gets\mathrm{null},\mathrm{null}$
  \If{$\mathrm{readable}$}
    \State $Q\gets\{\mathrm{function}\}$
    \State \textbf{if} $c\ne\varnothing$ \textbf{then} $Q\gets Q\cup\{\mathrm{arguments}\}$
    \State $(p_f,p_a)\gets J(x,\mathcal{F},c,Q)$
  \EndIf
  \State $A\gets\mathrm{Accept}(s,c,p_f,p_a,\tau_f,\tau_a)$ \Comment{Eq.~\ref{eq:gate}}
  \State $d\gets\mathrm{Feedback}(e,p_f,p_a,\tau_f,\tau_a,c)$
  \State \textbf{if} $A=1$ \textbf{or} $t=r$ \textbf{then break}
  \State $H\gets H\mathbin{\Vert}[(c,d)]$
\EndFor
\State \Return $c$ \textbf{if} $A=1$ \textbf{else} $c_0$ \Comment{$c_0$: first proposal}
\end{algorithmic}
\end{algorithm}

\paragraph{Feedback before the user request.}
$H_t$ stores earlier records. The current record $(c_t,d_t)$ pairs proposal $c_t$ with feedback $d_t$ (probabilities, pass/fail flags, thresholds, and local errors). No-call skips the argument check. After rejection, if repairs remain, $\Vert$ adds $[(c_t,d_t)]$, a list containing this one record, to the end of $H_t$:
\begin{equation}
 H_{t+1}=H_t\mathbin{\Vert}[(c_t,d_t)].
\end{equation}
The LLM reads this history before the unchanged request and can change both function and arguments. Schemas remain available; system instructions stay separate.

Algorithm~\ref{alg:jbfc} rechecks up to $r+1$ proposals: the first plus repairs ($r=3$ by default and in experiments). Its \texttt{Prefix} function places JSON records, oldest first, before unchanged original messages. Empty history adds no prefix. Records include round numbers and mark proposals as not executed. Here $s=S(c)$ and $e$ lists local errors. Readable proposals receive \textit{Jev} checks even if their schema fails; unreadable ones receive local feedback. \textit{Jev} never receives history. Unasked $p_a$ stays null. Null required probabilities cannot pass the gate; invalid API responses stop the run. Reference answers stay out of model requests. API errors stop the run after transport retries, separate from repairs.

\subsection{Final Proposal}
When a proposal passes all applicable checks, we return it. If the repair limit is reached first, we return the first proposal, so a repair replaces the generator's answer only once it passes (Table~\ref{tab:rules} compares returning the last). We score the final proposal against the benchmark answers without running the function.

\subsection{Models and Methods}
The generator is the Azure OpenAI deployment \texttt{gpt-5-nano} (\texttt{gpt-5-nano-2025-08-07}), with reasoning effort \texttt{none} and at most 4,096 output tokens; \textit{Jev} is pinned to \texttt{jev-1.13.0}. We use Chat Completions through an APIM gateway and System One directly, and convert BFCL schemas to JSON Schema with API-safe function names. Generations cut off at the output limit or blocked by the provider's filter count as wrong. Direct and \textbf{JBFC} also run on the larger, costlier deployment \texttt{gpt-5.4-mini} (snapshot 2026-03-17) with the same settings. Table~\ref{tab:categories} averages three runs per generator, each with new initial proposals.

We compare seven methods, sharing one initial proposal per example. \emph{Direct} uses the initial proposal; \emph{Schema-only} repairs schema errors. \emph{Self-refine} uses generic self-review in all $r$ repairs, not the full Self-Refine method~\cite{madaan2023selfrefine}. \textbf{JBFC-F} and \textbf{JBFC-A} obtain applicable \texttt{Noul} judgments but expose and require only the function or argument verdict, plus schema checks. \textbf{JBFC-A} accepts no call on schema checks alone. \textbf{JBFC-L} shares \textbf{JBFC}'s settings and initial proposal but shows only the latest rejected proposal and feedback. Neither model sees $r$ and nothing runs before the end, so a larger limit only continues trajectories: the first run ran all methods with $r=2$ and continued them to $r=3$; the \textit{Jev} methods ran again at threshold 0.5 (stated in their feedback) from the same initial proposals, \textbf{JBFC} to $r=10$ for Figure~\ref{fig:repairs}. Like \textbf{JBFC}, methods that stop at a passing proposal return the first if none passes.

\subsection{Measures, Cost, and Uncertainty}
We report call, function, and argument accuracy (the last given the correct function), fixes and new errors, acceptance, and repairs. We compare repairs with Direct, \textbf{JBFC} with \textbf{JBFC-L}, and the two final-proposal rules on matching examples and initial proposals, bootstrapping example IDs 2,000 times (seed 1729) for 95\% intervals after averaging each example over runs.

Costs count all generation and verification work, including the growing history and the shared initial call; times are mean API seconds without retry waits. Prices in USD per million uncached/cached/output tokens are 0.05/0.005/0.40 for \texttt{gpt-5-nano} and 0.75/0.075/4.50 for \texttt{gpt-5.4-mini}; \textit{Jev} input costs \$0.042 (output free), without gateway fees; one filtered generation without usage is left out.

\subsection{Results}
In Table~\ref{tab:categories}, \textbf{JBFC} raises mean accuracy from 64.1\% to 74.8\% (paired difference 10.7 points, 95\% interval 9.7--11.6; per run 10.8, 10.7, 10.4). Per run, it fixes 323--337 wrong initial proposals, breaks 7--10, and averages 0.64--0.65 repairs; 84--85\% of examples pass, 84--85\% of them correctly. \paragraph{Returning the first proposal.}
The rules differ only when no proposal passes; returning the last then makes unverified changes, which per run fix 26--33 calls and break 16--22 with \texttt{gpt-5-nano} but fix 10--14 and break 53--55, mostly correct no-calls, with \texttt{gpt-5.4-mini}. Keeping only accepted changes gains 1.4 points for \texttt{gpt-5.4-mini} and costs \texttt{gpt-5-nano} 0.4 (Table~\ref{tab:rules}).

\paragraph{A larger generator.}
Without \textit{Jev}, \texttt{gpt-5.4-mini} reaches 81.1\%, 6.4 points above \textbf{JBFC} with \texttt{gpt-5-nano} (95\% interval 5.1--7.7), at 3.3 times the cost and under half the time. \textbf{JBFC} raises it in every run, by 1.0 point on average (95\% interval 0.5--1.5); per run, it fixes 55--66 calls and breaks 27--39, mostly no-calls turned into accepted calls.

\paragraph{Comparison of methods.}
In Table~\ref{tab:main}, every repair method beats Direct (paired 95\% intervals above zero): schema repair by 2.0 points, self-refine 6.3, \textbf{JBFC-F} 9.5, \textbf{JBFC-A} 8.7, and \textbf{JBFC-L} 9.8. Self-refine makes four proposals per request yet trails the \textit{Jev}-based methods (1.4 to 1.6).

\paragraph{Why no-call cases gain most.}
Direct calls the one, unrelated function in 179 of 240 Irrelevance examples. \textit{Jev} separates these from the 61 correct no-calls (median function probability 0.09 vs.\ 0.95), and the generator withholds 126 of 156 rejected calls; in live irrelevance, separation is weaker (0.53 vs.\ 0.87), and 160 of 379 are withheld. Where reference calls exist, \textbf{JBFC} rejects 216 of 463 wrong initial calls but fixes only 51: a verdict flags a wrong call, not the right one.

\paragraph{More repairs.}
In Figure~\ref{fig:repairs}, $r=10$ reaches 76.7\%, at 1.6 times the time and 1.9 times the cost of $r=3$; later passing proposals fix 70 examples (59 by withholding a call) and break 4.

\paragraph{Records as in-context examples.}
Each record pairs a call with \textit{Jev}'s verdict, so the history acts as labeled in-context examples, made without reference answers in 0.19~s per label at about \$0.06 per 1,000. As in many-shot learning~\cite{agarwal2024manyshot}, more examples help: with the same attempts, the full history beats the latest record by 1.1 points (\textbf{JBFC} minus \textbf{JBFC-L}, 95\% interval 0.4--1.7), though all are failed attempts at one request.

\subsection{Study Limits}
The verifier can accept a wrong call or share the generator's mistake, and feedback can introduce or reinforce errors. We use two generators, one verifier, and mostly English single-turn requests; Table~\ref{tab:main} and Figure~\ref{fig:repairs} come from one run, and public examples may appear in training data. Ten documented annotation errors stay. Settings were chosen on these examples, so gains may be optimistic; effort \texttt{none} is untuned, and one common limit may favor some methods.

\section{Conclusion}
Feeding back \textit{Jev}'s judgments as a history, \textbf{JBFC} with three repairs raised mean accuracy from 64.1\% to 74.8\% with \texttt{gpt-5-nano}, mostly by withholding unnecessary calls, and from 81.1\% to 82.1\% with \texttt{gpt-5.4-mini}, as it returns the first proposal when none passes.
