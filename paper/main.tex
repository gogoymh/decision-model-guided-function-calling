\begin{abstract}
Function-calling models must choose a function and input values that match the user's request. Correct format alone does not ensure correct choices. We present Jev-Backed Function Calling (\textbf{JBFC}), an inference-time method that uses TypeSafe's System One (Decision) model \textit{Jev} to check an LLM's proposed call. \textit{Jev} checks function choice and, when a call is present, its arguments with binary questions. If a required check fails, we add the proposal and judgments to a growing history placed before the original user request. The LLM uses this feedback to revise both the function and arguments. Acceptance requires all applicable binary checks and the schema check to pass on the same proposal. The repair limit is fixed at two. Our code compares seven methods on a 3,051-example Berkeley Function Calling Leaderboard (BFCL) subset, measuring call correctness, function choice, argument correctness, time, and cost. In one run with \texttt{gpt-5-nano}, \textbf{JBFC} raises call accuracy over direct calling from 63.8\% to 73.5\%, mostly by avoiding unnecessary calls, at about four times the cost. It has the highest call accuracy of the seven methods, and keeping all earlier feedback adds 0.7 points over showing only the latest rejection.
\end{abstract}

\section{Introduction}
To carry out a user's request correctly, a function-calling system must choose the right function and provide the right argument values. A language model, called the generator, makes these choices. However, a call can have the required format and still use the wrong function or values. For example, a travel assistant may choose the wrong booking function or swap the departure and destination. A JSON schema check verifies required inputs and their types, but cannot guarantee that the call matches the user's request.

Tool-use training and evaluation have improved function-calling systems~\cite{patil2024gorilla,qin2024toolllm,patil2025bfcl}. Even so, the generated function and arguments can still be wrong. We study whether checks from a separate decision model can guide the LLM to improve its next proposal before execution.

\textbf{JBFC} uses \textit{Jev}, TypeSafe's System One model, to answer binary questions about an LLM's function choice and arguments~\cite{typesafe2026models}. When a check fails, we keep the proposed call and its judgments and place all earlier records before the original user request. The LLM then proposes a new call using this accumulated feedback. It can change both the function and argument values. \textbf{JBFC} accepts a proposal only when all applicable binary checks and the schema check pass on that proposal.

Earlier work already uses checks and feedback to fix calls. ToolVerifier checks tool choice and parameters~\cite{mekala2024toolverifier}; ToolCritic gives feedback on tool-use errors~\cite{hamad2025toolcritic}. ReAct uses reasoning, actions, and observations to guide later steps~\cite{yao2023react}. \textbf{JBFC} also carries feedback forward in the prompt, but its feedback comes from checking proposed calls before execution. Our contribution is this specific use of two \textit{Jev} judgments and accumulated prompts, together with an evaluation of its effects and costs.

We compare \textbf{JBFC} with direct calling, schema repair, self-revision, single-check versions, and a latest-feedback version. A fixed repair limit of two controls the comparison. We measure errors fixed or introduced by repair, and keep call correctness separate from acceptance, time, and cost.

\paragraph{Tool use and benchmarks.}
Gorilla studies API-call generation~\cite{patil2024gorilla}; ToolLLM studies tool-use training and evaluation~\cite{qin2024toolllm}. BFCL tests function calling across many settings~\cite{patil2025bfcl}. We use its single-turn Python categories to study decisions made before a function runs. API-Bank offers dialogues with executable API calls~\cite{li2023apibank}. StableToolBench uses caching and simulation to handle changing APIs~\cite{guo2024stabletoolbench}. These suggest broader tests beyond our BFCL subset.

\paragraph{Checks and feedback.}
Self-Refine uses self-generated feedback~\cite{madaan2023selfrefine}, Reflexion uses written feedback~\cite{shinn2023reflexion}, and CRITIC uses feedback from tools~\cite{gou2024critic}. Self-correction can turn correct answers into wrong ones~\cite{huang2024selfcorrect}, so we measure both fixes and new errors. ToolVerifier compares alternatives to check tool choice and parameters separately~\cite{mekala2024toolverifier}. ToolCritic identifies tool-use errors and returns feedback~\cite{hamad2025toolcritic}. \textbf{JBFC} checks complete proposals with a fixed external model through an API and limits repairs.

\paragraph{Accumulated prompts.}
ReAct combines reasoning with actions and observations from an environment~\cite{yao2023react}. Our method uses a similar idea of carrying earlier feedback into the next prompt. Each record contains a proposed function call and verification results, rather than an execution result. The LLM receives all records before the unchanged user request. We do not require a generated reasoning trace or run functions during repair. Many-shot in-context learning often improves as prompts grow to hundreds or thousands of examples, and model-generated rationales kept only when their answers are correct can stand in for human-written ones~\cite{agarwal2024manyshot}. Our records are likewise model-generated examples, labeled by \textit{Jev} instead of reference answers.

\paragraph{\textit{Jev} as a judge.}
Li et al.'s \emph{JEV-as-a-Judge}~\cite{li2026jevjudge} checks finished outputs with probabilities for defined verdicts. If a verdict is uncertain, an independent, stronger judge decides. With fixed rules for when to use the stronger judge, it lowers judging cost while keeping similar accuracy on some tasks. It has limits on difficult reasoning, misleading answer styles, and writing judged without reference information. The study does not test tool or action selection inside agents. \textbf{JBFC} checks proposed function calls and returns failed checks to the same generator for revision. We test the specific design of \textbf{JBFC}.

\section{Method}
\subsection{Propose and Check a Call}
Let $x$ be the user request, $\mathcal{F}$ the available functions, and $G$ the generating LLM. A proposal is $c_t=(f_t,a_t)$, with function $f_t$ and arguments $a_t$, or $c_t=\varnothing$ for no call. We study single-call-or-no-call decisions.\footnote{We treat single-turn decisions as the basic unit of function calling. Parallel calling combines multiple such decisions, while multi-turn interactions repeat them with updated context. We therefore evaluate the verification and repair loop on this basic unit and exclude parallel and multi-turn settings from this study.} Local code checks readability, function availability, required arguments, and types. Write $S(c_t)=1$ when these checks pass.

\paragraph{Binary verification: \textbf{JBFC}.}
For each readable proposal, one \textit{Jev} request checks the function choice and, when a call is present, its arguments:
\begin{align}
 c_t&=G(H_t,x,\mathcal{F}),\\
 p_f^{(t)}&=J_f(x,\mathcal{F},c_t),\qquad
 p_a^{(t)}=J_a(x,\mathcal{F},c_t).
\end{align}
Here $H_t$ contains earlier proposals and feedback and is initially empty. The function \texttt{Noul} question asks whether the function choice, including no call, fits the request. The argument question checks required values, their support in the request, and their parameter roles. For no call, it is skipped and $p_a^{(t)}$ is undefined. A selected function with missing arguments still receives both checks. Both must pass for a call.

\subsection{Accept or Repair a Call}
Acceptance requires the schema check and all required \textit{Jev} checks to pass on the same proposal. The acceptance rule is
\begin{equation}
 A_t=\begin{cases}
 S(c_t)\,\mathbf{1}[p_f^{(t)}\geq\tau_f], & c_t=\varnothing,\\
 S(c_t)\,\mathbf{1}[p_f^{(t)}\geq\tau_f]\,
 \mathbf{1}[p_a^{(t)}\geq\tau_a], & \text{otherwise}.
 \end{cases}
\label{eq:gate}
\end{equation}
\texttt{Noul} returns the probability of yes, with no separate confidence field~\cite{typesafe2026noul,typesafe2026confidence}. We start with $\tau_f=\tau_a=0.8$, untuned defaults chosen for this experiment.

\begin{algorithm}[t]
\caption{\textbf{JBFC}: verification and prompt repair}
\label{alg:jbfc}
\footnotesize
\begin{algorithmic}[1]
\Require Request $x$, functions $\mathcal{F}$, generator $G$, \textit{Jev} $J$,
\Statex \hspace{\algorithmicindent}repair limit $r$, thresholds $\tau_f,\tau_a$
\State $H\gets[\,]$
\For{$t=0,\ldots,r$}
  \State $c\gets G(\mathrm{Prefix}(H,x),\mathcal{F})$
  \State $(s,e,\mathrm{readable})\gets\mathrm{SchemaCheck}(c,\mathcal{F})$
  \State $p_f,p_a\gets\mathrm{null},\mathrm{null}$
  \If{$\mathrm{readable}$}
    \State $Q\gets\{\mathrm{function}\}$
    \State \textbf{if} $c\ne\varnothing$ \textbf{then} $Q\gets Q\cup\{\mathrm{arguments}\}$
    \State $(p_f,p_a)\gets J(x,\mathcal{F},c,Q)$
  \EndIf
  \State $A\gets\mathrm{Accept}(s,c,p_f,p_a,\tau_f,\tau_a)$ \Comment{Eq.~\ref{eq:gate}}
  \State $d\gets\mathrm{Feedback}(e,p_f,p_a,\tau_f,\tau_a,c)$
  \State \textbf{if} $A=1$ \textbf{or} $t=r$ \textbf{then break}
  \State $H\gets H\mathbin{\Vert}[(c,d)]$
\EndFor
\State \Return $c$
\end{algorithmic}
\end{algorithm}

\paragraph{Feedback before the user request.}
$H_t$ stores earlier records. The current record $(c_t,d_t)$ pairs proposal $c_t$ with feedback $d_t$ (probabilities, pass/fail flags, thresholds, and local errors). No-call skips the argument check. After rejection, if repairs remain, $\Vert$ adds $[(c_t,d_t)]$, a list containing this one record, to the end of $H_t$:
\begin{equation}
 H_{t+1}=H_t\mathbin{\Vert}[(c_t,d_t)].
\end{equation}
The LLM reads this history before the unchanged request and can change both function and arguments. Schemas remain available; system instructions stay separate.

Algorithm~\ref{alg:jbfc} rechecks up to $r+1$ proposals: the first plus repairs (Python default $r=3$; $r=2$ in experiments). Its \texttt{Prefix} function places JSON records, oldest first, before unchanged original messages. Empty history adds no prefix. Records include round numbers and mark proposals as not executed. Here $s=S(c)$ and $e$ lists local errors. Readable proposals receive \textit{Jev} checks even if their schema fails; unreadable ones receive local feedback. \textit{Jev} never receives history. Unasked $p_a$ stays null. Null required probabilities cannot pass the gate; invalid API responses stop the run. Reference answers stay out of model requests. API errors stop the run after transport retries, separate from repairs.

\subsection{Final Proposal}
When a proposal passes all applicable checks, we return it. If the repair limit is reached first, we return the last proposal even if it fails a check (\texttt{execute\_last}). We score the final proposal against the benchmark answers without running the function.

\subsection{Models and Methods}
The generator is the Azure OpenAI deployment \texttt{gpt-5-nano} (\texttt{gpt-5-nano-2025-08-07}), with reasoning effort \texttt{none} and at most 4,096 output tokens; \textit{Jev} is pinned to \texttt{jev-1.13.0}. We use Chat Completions and System One through an APIM gateway (System One directly for repairs beyond $r=7$) and convert BFCL schemas to JSON Schema with API-safe function names. Generations cut off at the output limit or blocked by the provider's filter are unreadable proposals and count as wrong. Direct also runs once with the larger, costlier deployment \texttt{gpt-5.4-mini} under the same settings (Table~\ref{tab:categories}).

We compare seven methods, sharing one initial proposal per example. \emph{Direct} uses the initial proposal; \emph{Schema-only} repairs schema errors. \emph{Self-refine} uses generic self-review in all $r$ repairs, not the full Self-Refine method~\cite{madaan2023selfrefine}. \textbf{JBFC-F} and \textbf{JBFC-A} obtain applicable \texttt{Noul} judgments but expose and require only the function or argument verdict, plus schema checks. \textbf{JBFC-A} accepts no call on schema checks alone. \textbf{JBFC} requires all applicable checks. \textbf{JBFC-L} shares its settings and initial proposal but shows only the latest rejected proposal and feedback. Other repair methods show all earlier records before the request. With $r=2$, repair methods make at most three proposals, and the \textbf{JBFC} and \textbf{JBFC-L} prompts differ only in the second repair. Figure~\ref{fig:repairs} varies $r$ for \textbf{JBFC}. Since neither model sees $r$ and nothing runs before the end, we continue the $r=2$ trajectories of Table~\ref{tab:main} that reach the limit up to $r=10$ and cut them at each limit.

\subsection{Measures, Cost, and Uncertainty}
We report call accuracy, function accuracy, and argument accuracy given the correct function; comparing initial and final proposals shows fixes and new errors. We also record acceptance, repairs, API errors, and Brier scores.

Costs count all generation and verification work, including the growing history and the shared initial call; times are mean API seconds without retry waits. Prices in USD per million uncached/cached/output tokens are 0.05/0.005/0.40 for \texttt{gpt-5-nano} and 0.75/0.075/4.50 for \texttt{gpt-5.4-mini}; \textit{Jev} input costs \$0.042 (output free). Gateway fees are excluded.

We compare repairs with Direct and \textbf{JBFC} with \textbf{JBFC-L}, matching examples and initial proposals, and bootstrap example IDs 2,000 times with seed 1729 for 95\% intervals.

\subsection{Results}
In Table~\ref{tab:categories}, \textbf{JBFC} raises accuracy from 63.8\% to 73.5\% (paired difference 9.7 points, 95\% interval 8.5--11.0). It fixes 339 wrong initial proposals, breaks 44 correct ones, and uses 0.75 repairs per example; 31.8\% of examples reach the limit without passing, and the 68.4\% that pass are 90.6\% correct.

\paragraph{Comparison of methods.}
In Table~\ref{tab:main}, every repair method beats Direct (paired 95\% intervals above zero): schema repair by 2.0 points, self-refine 6.1, \textbf{JBFC-F} 8.8, \textbf{JBFC-A} 9.2, and \textbf{JBFC-L} 9.0. Self-refine makes three proposals per request yet trails the \textit{Jev}-based methods, which average 1.5 to 1.8.

\paragraph{Why no-call cases gain most.}
Every Irrelevance example offers one unrelated function, and Direct calls it in 179 of 240 cases (25.4\% and 27.1\% in two other runs). \textit{Jev}'s function question separates these calls from the 61 correct no-calls (median probability 0.09 vs.\ 0.95). \textbf{JBFC} rejects 166 of the calls, and after the feedback the generator withholds 118; the 62 errors are 13 accepted calls, 48 calls kept after rejection, and one correct no-call turned into a call. In live irrelevance (2.3 functions on average, real requests), \textit{Jev} separates less sharply (0.53 vs.\ 0.87), the generator drops only 158 of 432 rejected calls, and 25 correct no-calls become calls. In categories with reference calls, \textbf{JBFC} rejects 334 of 463 wrong initial calls but fixes only 63 and breaks 18: a binary verdict says that a call is wrong, not which call is right, while withholding an unnecessary call is the obvious repair.

\paragraph{More repairs.}
Accuracy rises from 72.6\% at $r=1$ to 78.6\% at $r=10$ (Figure~\ref{fig:repairs}); from $r=2$, time grows 2.5-fold and cost triples. Of the 194 examples that turn correct from $r=2$ to $r=10$ (39 turn wrong), 178 are irrelevance cases where the generator finally makes no call; only 52 end with a passing proposal (exhaustion falls from 31.8\% to 29.2\%).

\paragraph{Records as in-context examples.}
Each record pairs a generated call with \textit{Jev}'s verdict, so the history acts as labeled in-context examples, made without reference answers in 0.30 seconds per label on average (the generator takes 1.35) at about \$0.06 per 1,000. As in many-shot learning~\cite{agarwal2024manyshot}, more examples help: with the same attempts, all records beat the latest one by 0.7 points (\textbf{JBFC} minus \textbf{JBFC-L}, 95\% interval 0.1--1.4), and accuracy rises with the limit, which also adds attempts. Unlike many-shot prompts, these are failed attempts at the same request; help for other requests is untested.

\subsection{Study Limits}
The verifier can accept a wrong call or share the generator's mistake, repair can introduce errors, and the growing feedback can reinforce a mistake or distract the LLM; higher acceptance alone does not show improvement.

The study uses one model pair, mostly English requests, single-turn calls, and one run per method, so run-to-run variation is unknown; public examples may overlap with training data. Ten documented annotation inconsistencies stay in the main score; in six, reference values contradict declared types, so schema-checked methods cannot accept a correct call. Thresholds and reasoning effort \texttt{none} are untuned, and one common repair limit may favor some methods.

\section{Conclusion}
\textbf{JBFC} feeds \textit{Jev}'s function and argument judgments back to the LLM as a history placed before the original request. In one run with \texttt{gpt-5-nano} and two repairs, it raised accuracy from 63.8\% to 73.5\% at about four times the cost, mostly by withholding unnecessary calls. The history, in effect \textit{Jev}-labeled in-context examples, added 0.7 points over the latest feedback alone, and ten repairs reached 78.6\% at about three times the cost of two.
