\begin{abstract}
Function-calling models must choose a function and input values that match the user's request. Correct format alone does not ensure correct choices. We present Jev-Backed Function Calling (\textbf{JBFC}), an inference-time method that uses TypeSafe's System One (Decision) model \textit{Jev} to check an LLM's proposed call. \textit{Jev} answers two binary questions: whether the function is appropriate and whether its arguments are correct. If either check fails, we add the proposal and judgments to a growing history placed before the original user request. The LLM uses this feedback to revise both the function and arguments. Acceptance requires both checks and the schema check to pass on the same proposal. A repair limit is chosen on development data and fixed before testing. Our code compares six methods on 2,748 test examples from a 3,051-example Berkeley Function Calling Leaderboard (BFCL) subset, measuring call correctness, function choice, argument correctness, time, and cost. Experiments have not yet been run. They will test whether accumulated verification feedback improves calls and whether repairs justify their added cost.
\end{abstract}

\section{Introduction}
To carry out a user's request correctly, a function-calling system must choose the right function and provide the right argument values. A language model, called the generator, makes these choices. However, a call can have the required format and still use the wrong function or values. For example, a travel assistant may choose the wrong booking function or swap the departure and destination. A JSON schema check verifies required inputs and their types, but cannot guarantee that the call matches the user's request.

Tool-use training and evaluation have improved function-calling systems~\cite{patil2024gorilla,qin2024toolllm,patil2025bfcl}. Even so, the generated function and arguments can still be wrong. We study whether checks from a separate decision model can guide the LLM to improve its next proposal before execution.

\textbf{JBFC} uses \textit{Jev}, TypeSafe's System One model, to answer binary questions about an LLM's function choice and arguments~\cite{typesafe2026models}. When a check fails, we keep the proposed call and its judgments and place all earlier records before the original user request. The LLM then proposes a new call using this accumulated feedback. It can change both the function and argument values. \textbf{JBFC} accepts a proposal only when both binary checks and the schema check pass on that proposal.

Earlier work already uses checks and feedback to fix calls. ToolVerifier checks tool choice and parameters~\cite{mekala2024toolverifier}; ToolCritic gives feedback on tool-use errors~\cite{hamad2025toolcritic}. ReAct uses reasoning, actions, and observations to guide later steps~\cite{yao2023react}. \textbf{JBFC} also carries feedback forward in the prompt, but its feedback comes from checking proposed calls before execution. Our contribution is this specific use of two \textit{Jev} judgments and accumulated prompts, together with an evaluation of its effects and costs.

We compare \textbf{JBFC} with direct calling, schema repair, self-revision, and single-check versions. A repair limit chosen on development data controls the comparison. We measure errors fixed or introduced by repair, and keep call correctness separate from acceptance, time, and cost.

\paragraph{Tool use and benchmarks.}
Gorilla studies API-call generation~\cite{patil2024gorilla}; ToolLLM studies tool-use training and evaluation~\cite{qin2024toolllm}. BFCL tests function calling across many settings~\cite{patil2025bfcl}. We use its single-turn Python categories to study decisions made before a function runs. API-Bank offers dialogues with executable API calls~\cite{li2023apibank}. StableToolBench uses caching and simulation to handle changing APIs~\cite{guo2024stabletoolbench}. These suggest broader tests beyond our BFCL subset.

\paragraph{Checks and feedback.}
Self-Refine uses self-generated feedback~\cite{madaan2023selfrefine}, Reflexion uses written feedback~\cite{shinn2023reflexion}, and CRITIC uses feedback from tools~\cite{gou2024critic}. Self-correction can turn correct answers into wrong ones~\cite{huang2024selfcorrect}, so we measure both fixes and new errors. ToolVerifier compares alternatives to check tool choice and parameters separately~\cite{mekala2024toolverifier}. ToolCritic identifies tool-use errors and returns feedback~\cite{hamad2025toolcritic}. \textbf{JBFC} checks complete proposals with a fixed external model through an API and limits repairs.

\paragraph{Accumulated prompts.}
ReAct combines reasoning with actions and observations from an environment~\cite{yao2023react}. Our method uses a similar idea of carrying earlier feedback into the next prompt. Each record contains a proposed function call and verification results, rather than an execution result. The LLM receives all records before the unchanged user request. We do not require a generated reasoning trace or run functions during repair.

\paragraph{\textit{Jev} as a judge.}
Li et al.'s \emph{JEV-as-a-Judge}~\cite{li2026jevjudge} checks finished outputs with probabilities for defined verdicts. If a verdict is uncertain, an independent, stronger judge decides. With fixed rules for when to use the stronger judge, it lowers judging cost while keeping similar accuracy on some tasks. It has limits on difficult reasoning, misleading answer styles, and writing judged without reference information. The study does not test tool or action selection inside agents. \textbf{JBFC} checks proposed function calls and returns failed checks to the same generator for revision. We test the specific design of \textbf{JBFC}.

\section{Method}
\subsection{Propose and Check a Call}
Let $x$ be the user request, $\mathcal{F}$ the available functions, and $G$ the generating LLM. A proposal is $c_t=(f_t,a_t)$, with function $f_t$ and arguments $a_t$, or $c_t=\varnothing$ for no call. We study single-call-or-no-call decisions.\footnote{We treat single-turn decisions as the basic unit of function calling. Parallel calling combines multiple such decisions, while multi-turn interactions repeat them with updated context. We therefore evaluate the verification and repair loop on this basic unit and exclude parallel and multi-turn settings from this study.} Local code checks readability, function availability, required arguments, and types. Write $S(c_t)=1$ when these checks pass.

\paragraph{Binary verification: \textbf{JBFC}.}
For each readable proposal, one \textit{Jev} request checks the function choice and, when a call is present, its arguments:
\begin{align}
 c_t&=G(H_t,x,\mathcal{F}),\\
 p_f^{(t)}&=J_f(x,\mathcal{F},c_t),\qquad
 p_a^{(t)}=J_a(x,\mathcal{F},c_t).
\end{align}
Here $H_t$ contains earlier proposals and feedback and is initially empty. The function \texttt{Noul} question asks whether the function choice, including no call, fits the request. The argument question checks required values, their support in the request, and their parameter roles. For no call, it is skipped and $p_a^{(t)}$ is undefined. A selected function with missing arguments still receives both checks. Both must pass for a call.

\subsection{Accept or Repair a Call}
The acceptance rule is
\begin{equation}
 A_t=\begin{cases}
 S(c_t)\,\mathbf{1}[p_f^{(t)}\geq\tau_f], & c_t=\varnothing,\\
 S(c_t)\,\mathbf{1}[p_f^{(t)}\geq\tau_f]\,
 \mathbf{1}[p_a^{(t)}\geq\tau_a], & \text{otherwise}.
 \end{cases}
\label{eq:gate}
\end{equation}
Noul returns the probability of yes, with no separate confidence field~\cite{typesafe2026noul,typesafe2026confidence}. We start with $\tau_f=\tau_a=0.8$, untuned defaults chosen for this experiment.

\begin{algorithm}[t]
\caption{\textbf{JBFC}: verification and prompt repair}
\label{alg:jbfc}
\footnotesize
\begin{algorithmic}[1]
\Require Request $x$, functions $\mathcal{F}$, generator $G$, \textit{Jev} $J$,
\Statex \hspace{\algorithmicindent}repair limit $r$, thresholds $\tau_f,\tau_a$, final policy
\State $H\gets[\,]$
\For{$t=0,\ldots,r$}
  \State $c\gets G(\mathrm{Prefix}(H,x),\mathcal{F})$
  \State $(s,e,\mathrm{readable})\gets\mathrm{SchemaCheck}(c,\mathcal{F})$
  \State $p_f,p_a\gets\mathrm{null},\mathrm{null}$
  \If{$\mathrm{readable}$}
    \State $Q\gets\{\mathrm{function}\}$
    \State \textbf{if} $c\ne\varnothing$ \textbf{then} $Q\gets Q\cup\{\mathrm{arguments}\}$
    \State $(p_f,p_a)\gets J(x,\mathcal{F},c,Q)$
  \EndIf
  \State $A\gets\mathrm{Accept}(s,c,p_f,p_a,\tau_f,\tau_a)$ \Comment{Eq.~\ref{eq:gate}}
  \State $d\gets\mathrm{Feedback}(e,p_f,p_a,\tau_f,\tau_a,c)$
  \State $\mathrm{Record}(t,c,d,A)$
  \State \textbf{if} $A=1$ \textbf{or} $t=r$ \textbf{then break}
  \State $H\gets H\mathbin{\Vert}[(c,d)]$
\EndFor
\State $\mathrm{FinalDispatch}(c,A,\mathrm{policy})$
\end{algorithmic}
\end{algorithm}

\paragraph{Feedback before the user request.}
For a rejected proposal, $d_t$ contains probabilities, pass/fail flags, thresholds, and local errors. No-call marks the argument check as skipped, with no verdict or probability. If repairs remain, we append the record:
\begin{equation}
 H_{t+1}=H_t\mathbin{\Vert}[(c_t,d_t)].
\end{equation}
\texttt{Prefix} places JSON records, oldest first, before unchanged original messages. Empty history adds no prefix. Records include round numbers and mark proposals as not executed. The LLM can change both function and arguments. Schemas remain available; system instructions stay separate. In Algorithm~\ref{alg:jbfc}, $s=S(c)$ and $e$ lists local errors. Readable proposals receive \textit{Jev} checks even if their schema fails; unreadable ones receive local feedback. \textit{Jev} never receives history. Unasked $p_a$ stays null. Null required probabilities cannot pass the gate; invalid API responses stop the run.

Algorithm~\ref{alg:jbfc} summarizes the loop: $r+1$ proposals at most, with fresh checks each time. Reference answers stay out of model requests. API errors stop without dispatch after transport retries, separate from repairs.

\subsection{Return and Record the Result}
The final dispatch returns the proposal under \texttt{execute\_last}, even if rejected. The optional \texttt{abstain} policy withholds rejected calls, which are still scored offline. Only this boundary can run an application callback. Benchmark dispatch is simulated; no function executes during repair or scoring.

Records save stopping reasons, model versions, usage, and timings; manifests save data, code hashes, routes, and settings. Keys stay outside records. Methods share the first proposal for each example and run, charged to each method with its own later work.

For categories with reference calls, the original Python abstract syntax tree (AST) checker tests function names and arguments against allowed answers. Irrelevance categories require no call. Category scores show what the larger live categories may hide in the average.

BFCL's ``multiple'' categories offer several functions to choose from, without parallel calls. We exclude parallel calls, multi-turn state, web search, memory, and live execution. ``Live'' is a category name. AST checks compare call structure with annotated alternatives; passing them does not prove execution success, authorization, or task completion.

\subsection{Models and Methods}
The generator is \texttt{gpt-5.4-mini-2026-03-17}, with reasoning effort \texttt{none}; \textit{Jev} is pinned to \texttt{jev-1.13.0}. We use OpenAI Responses and System One through an APIM gateway, preserve supplied schemas, and plan three repeated runs with fixed prompts. Models, thresholds, and prompts can be changed, but their selection must use development data before the test setup is frozen.

We compare six methods. \emph{Direct} uses the initial LLM proposal. \emph{Schema-only} repairs code-detected errors. \emph{Self-refine} uses a fixed self-review instruction, a generic control rather than the full Self-Refine method~\cite{madaan2023selfrefine}. \mbox{\textbf{JBFC-F}} and \mbox{\textbf{JBFC-A}} obtain the applicable Noul judgments but use only the function or argument check, respectively, with schema checks. Feedback exposes only that check. With no argument check, \textbf{JBFC-A} accepts no call on schema checks alone. \textbf{JBFC} requires all applicable checks. Repair methods keep earlier proposals and feedback before the original request and share a maximum proposal count. Actual time and cost can differ.

\paragraph{Choosing the repair limit.}
We choose $r$ before testing. The initial candidates are $\mathcal{R}=\{0,1,2,3,4,5\}$, a configurable search range. \textbf{JBFC} has no built-in limit of five. In three development runs, we allow up to $\max\mathcal{R}$ repairs and stop early when all applicable checks pass. Neither model sees the limit, and no function runs during repair. Each smaller limit can therefore be tested on the same saved sequence without more API calls. \textit{Jev} thresholds stay at $0.8$ during this search.

We choose the limit with the highest final-call accuracy on development data. Ties choose the smaller limit:
\begin{equation}
 r^*=\min\arg\max_{r\in\mathcal{R}}\widehat{\mathrm{Acc}}_{\mathrm{dev}}(r).
\end{equation}
The score covers 302 development examples per run, excluding the one live-relevance example. We save the chosen limit, settings, and development-record hashes before three test runs compare all six methods. Test scores never choose the limit. Table~\ref{tab:diagnostics} shows the development search for \textbf{JBFC}. Optional smaller-limit and \texttt{abstain} analyses use only saved \textbf{JBFC} sequences. Cost and time cover only the selected prefix. With $r=0$, the initial proposal is checked but never revised.

\subsection{Measures, Cost, and Uncertainty}
We report final call accuracy, function accuracy, and argument accuracy conditional on the correct function. Every score includes its denominator. Live relevance is excluded from these accuracy measures and reported separately. We compare initial and final candidates to identify function changes, argument fixes, and new errors after feedback.

Acceptance is distinct from correctness. Coverage is the fraction accepted; accepted precision is accuracy among accepted calls. Selective risk is one minus this precision. False acceptance conditions on incorrect calls, and false rejection on correct calls. We also record corrections, regressions, repairs, API errors, and Brier scores where matching probability and correctness labels exist. These measures show whether feedback corrects rejected errors or instead introduces new ones.

\subsection{Study Limits}
The verifier can accept a wrong call or share the generator's mistake. Repair can introduce errors, and later proposals may differ from development examples. Accumulated feedback can reinforce an earlier mistake or distract the LLM from the original request. The history also grows with each repair, increasing context use and cost. Binary verdicts do not explain how to fix an error. Higher acceptance alone does not show improvement.

The study uses one model pair, mostly English requests, and single-turn calls. Public examples may overlap with training data. We keep four documented annotation inconsistencies in the main score. The candidate grid and small development set can affect the chosen repair limit. A common limit chosen for \textbf{JBFC} may disadvantage other methods. Further studies should tune each method separately and test more models and domains. API failures and incomplete runs remain visible. Conclusions must follow measured results, including no gain or worse performance.

\section{Conclusion}
\textbf{JBFC} uses \textit{Jev}'s function and argument judgments as accumulated prompt feedback. After a failed check, earlier proposals and judgments appear before the original user request, allowing the LLM to revise the complete call. A development-chosen repair limit bounds this process. The code separates correctness, acceptance, and cost. Experiments remain to be run; they will test whether this feedback improves function calling and whether the gains justify the added work.
